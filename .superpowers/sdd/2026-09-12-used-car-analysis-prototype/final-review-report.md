### Issues

#### Critical (Must Fix)

1. **The default fallback cannot ingest a listing.** File: `src/app/api/analyses/route.ts:8`; `src/features/submission/submission-form.tsx:44`; `src/app/api/analyses/[publicId]/submissions/handler.ts:131`; `src/analysis/pipeline.ts:313`. The creation API accepts only `locale` and `listingUrl`, so `analysis_inputs.pasted_text` is never set. When fetching is disabled by default or capture fails, `captureListing` builds a snapshot from an empty string. The report's later “Add seller information” form sends pasted listing text as a *seller answer*; it neither populates the fallback snapshot's description/facts nor preserves buyer-entered listing provenance. Image uploads likewise become seller-provided images, not buyer-provided listing screenshots. Consequently the documented paste-and-screenshot fallback cannot recover the listing's vehicle data, and the primary default flow produces a near-empty vehicle report. Add an explicit buyer-provided fallback submission path that stores pasted text and screenshots, marks their provenance correctly, extracts usable fields, and reruns capture/normalization/baseline as required. Cover the disabled-fetch and blocked-fetch journeys end to end.

2. **The live verdict effectively has one outcome.** File: `src/analysis/baseline-checks.ts:279`; `src/analysis/pipeline.ts:240`; `src/domain/verdict.ts:3`. Baseline checks unconditionally add `missing_inspection_images` as an **open important** finding, including when image references exist but are merely unclassified. `calculateVerdict` therefore always chooses `proceed_cautiously` unless a finding is confirmed. No production pipeline path creates a confirmed finding: baseline findings are open and `findingFromInsight` also hardcodes open (`src/analysis/pipeline.ts:438`). Further, listing and correction facts and baseline evidence have confidence `0.5`, so `confidenceInputFromRun` yields a low floor even when data is present. `worth_viewing`, `likely_skip`, and moderate/high confidence are unreachable through the real worker flow; the seeded E2E verdict change is a fixture, as the Task 14 report says. Make image coverage conditional on actual classified coverage, define a corroboration/confirmation path with appropriate confidence inputs, and add full-pipeline cases that reach all three verdicts without injecting a prebuilt report.

#### Important (Should Fix)

3. **Valid Luna research findings are dropped because their sources are never persisted as evidence.** File: `src/analysis/pipeline.ts:530`; `src/analysis/pipeline.ts:538`; `src/analysis/assemble-report.ts:45`. `LunaInsightProvider` accepts findings only when they cite their registered `source.id` (`src/insights/luna.ts:57`). The stage maps findings and image observations but discards `insight.sources`; its `EnrichOutput.evidence` contains only supplement evidence. Assembly then rejects every important/critical Luna finding citing that source ID as `finding_without_evidence`. The passing integration case at `tests/integration/progressive-report.test.ts:317` uses a mock that cites preexisting input evidence and would fail Luna's own provenance rule. Convert accepted sources into scoped source snapshots and evidence, retain their URLs/applicability/verification, and test the production provider contract through assembly.

4. **Supplement lineage loses the accepting run ID.** File: `src/server/repositories/analyses.ts:405`. The query omits `run_id`, but line 418 reads `row.run_id` as `acceptedRunId`. On a later image-only supplement run, `supplementEvidence` and the image capability fallback use the *current* run ID for earlier supplements (`src/analysis/pipeline.ts:163`, `src/analysis/pipeline.ts:486`). Inherited baseline evidence keeps earlier IDs, so the old materials are minted again under new IDs and treated as current-run evidence. This breaks stable provenance and can duplicate historical supplement evidence in the assembled report. Select `run_id`, verify it is present, and add a two-supplement integration case that checks evidence IDs, run ownership, and the final report.

5. **Estonian reports contain English analysis and seller messages.** File: `src/analysis/baseline-checks.ts:189`; `src/features/report/report-view.tsx:95`; `src/features/report/seller-message.tsx:29`. Baseline titles, explanations, next actions, and instructions are hardcoded English. The report renders these strings as-is, labels them with `lang={report.locale}`, and copies the English instructions into the seller message even in ET. The language switch translates chrome and verdict labels, but not the buyer's core report or message. Store locale-neutral finding/action keys with localized rendering, or generate and persist both locales while retaining genuine source excerpts in their original language. Cover an actual deterministic ET report and copied seller message, not only UI headings.

6. **The research cache and source collection are not connected to the production worker.** File: `scripts/worker.ts:28`; `src/analysis/pipeline.ts:416`. The worker supplies no `researchProvider`, so every production research stage returns `research_unavailable`; `CachedResearchProvider` and its repository are otherwise unused by the live pipeline. The official status remains honestly `not_checked`, but the specified applicable-source research and reusable cache never contribute to a report or reduce Luna calls. Wire a compliant upstream source strategy through `CachedResearchProvider`, or explicitly narrow the prototype acceptance criteria and documentation if this stage is intentionally unavailable. Exercise a cache hit and an unavailable-source path through the worker composition.

7. **Uploaded documents are accepted but never analyzed.** File: `src/analysis/pipeline.ts:519`; `src/server/repositories/analyses.ts:431`. PDF submissions create unverified evidence and a new run, yet only images are signed for the insight provider; `documentText` is a generic MIME placeholder and no PDF bytes/text enter baseline or Luna. An invoice cannot corroborate a maintenance claim or change the verdict despite the advertised document-update flow. Add bounded, safe PDF text extraction or a clearly scoped document review path that produces evidence tied to the uploaded source; keep an unreadable document explicitly unverified. Test a real document supplement through the run.

### Recommendations

- Fix the two product-path failures first, then rerun focused browser journeys using the real worker. Preserve distinct buyer, seller, listing, and uploaded provenance throughout fallback and supplements.
- Add one production-shape Luna contract test through `enrich` and assembly; mocked provider results must satisfy the same source-ID rule as `LunaInsightProvider`.
- Re-run the reported full gate after access, evidence, or worker changes. Re-review those changed boundaries. The ongoing manual evidence follow-up should be incorporated into the PR outcome separately; it is not itself a code finding.

### Assessment

**Spec compliance:** Partial. The private access boundary, progressive baseline, offline copy, and UI shell broadly follow the spec. The default fallback, three-way verdict, complete ET content, document analysis, and research-cache integration do not meet material Global Constraints and acceptance criteria.

**Code quality:** Sound core separation and defensive boundaries, but several production paths are disconnected from their tested abstractions. Tests are extensive yet rely on seeded or mocked reports where the real pipeline behavior differs.

**Ready to merge?** No.

**Reasoning:** Two core buyer journeys are broken in production configuration, and the optional enrichment and supplement evidence paths have material gaps. The clean reported gate and existing PR are valuable but do not establish the required product invariants.
