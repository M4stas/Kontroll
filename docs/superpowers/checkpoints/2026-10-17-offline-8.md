# Checkpoint 8: save a report on this device

Part A of the [offline reports plan](../plans/2026-10-17-offline-reports.md), based
on `main` at `0ba8bd5`. PR #37 merged. The user confirmed the remaining cookie
and restart checks and accepted Part A on 2026-10-19, then approved Part B.

## What you will see

The report cards have Save on this device, then a save date, kept-until date,
Update and Remove. The front page lists saved reports with Open and Remove.
Both saved copies and report access cookies last 30 days after Save or Update.
Opening reports still requires a connection in this checkpoint.

## How to check

1. Open a private report and save it. Check the saved and kept-until dates.
2. Open the front page. Open the report from its saved row.
3. Save a second report. Remove the first and confirm the second stays saved.
4. Add a seller answer, wait for review, open the cards, and Update when the
   newer-version notice appears. Repeat in Estonian.
5. Follow the two-minute development expiry procedure in
   [local development](../../local-development.md#report-access-and-limitations).
6. Clear cookies without clearing site storage. Check access is denied while
   the saved copy remains listed. Open the original private link to regain access.
7. Quit and reopen the browser, then open a saved report without its private
   fragment. Its persistent cookie should still authorize access.

Test concurrency and timeout flags accommodate worker-CLI bootstrap under load;

Coverage includes cookie Max-Age and renewal authorization, unchanged retry
origin checks, schema/expiry cleanup, quota and unavailable storage, retention
on 401/403, ordered writes, per-report removal, two-tab notifications, strip
visibility and dates, and front-page localization.

Independent review found and fixed two races:

- Cleanup of an invalid snapshot could erase a valid replacement. Validation
  and conditional deletion now occur in the same readwrite transaction. Tests
  use a separate connection to replace both get/list snapshots before cleanup.
- A save fetching in one tab could restore a copy removed in another. A small
  shared removal token is checked while holding the IndexedDB write lock.
  Separate-module regression tests first returned `saved`, then `cancelled`
  after the fix. Explicit saves started after removal still work.

Independent code review and the final privacy/concurrency re-review are clean.
The existing demo lint warnings are unchanged. A nonblocking follow-up remains:
front-page Remove retains its row on storage failure but provides no error text.

## Storage decision

The database remains `kontroll-offline`, version 1, store `reports`, with
`schemaVersion: 1` records. Report JSON and checklist data stay in IndexedDB.
The cross-tab removal fix adds random localStorage removal tokens keyed by report
ID. These small markers remain after removal to invalidate older pending saves;
they contain identifiers but no report contents. Browsers that allow IndexedDB
but block localStorage cannot save. A failed token write rejects Remove before
deleting data. This is the documented tradeoff for preserving removal across tabs
without changing the database schema or losing existing copies.
